# コードコメント規約

コードを追加・変更・reviewするときに適用する。宣言のドキュメントコメントは用途と契約を、本文の通常コメントは処理の流れと判断を説明する。必須の存在・配置・形式は利用先の機械検査で確認し、内容の正確さ・十分さはreviewで確認する。

## 宣言のドキュメントコメント

名前付きの型・関数・メソッドを基本対象とする。公開APIや境界に限らず、非公開の主要な業務処理・内部処理にも付ける。利用者や保守者が知るべき役割、入力の前提、結果、副作用、失敗時の挙動を、必要なものに絞って記す。使わない項目を埋めるための定型文は要らない。

言語の通常の形式（C#のXMLドキュメントコメント、TypeScript／JavaScriptのJSDoc、Pythonのdocstringなど）を使う。test関数・メソッドも対象とし、`test(...)`／`it(...)`等の呼び出し形式にも、たとえば呼び出し直前のJSDocをその呼び出しに結び付けるなど、frameworkに適した位置を利用先で定める。公開宣言だけを検査する既定設定では非公開処理や呼び出し型testまで検査したことにならない。

## 本文の通常コメント

構文の逐語訳より、そこで何を確定・取得・加工・保存するか、どんな分岐を扱うかが分かる説明を置く。必須位置では「自明」を理由に省略しない。読解に必要なら数行で一段落の目的を説明してよい。

| 対象 | 置く説明と位置 |
| --- | --- |
| 分岐の各枝 | 条件や枝ごとに扱う処理の意味を、条件・ラベルの直前または枝の先頭に記す。`else`／`case`等を親の総論で代用しない。同じ処理に合流するcase群などは利用先で対応を定める。 |
| 反復 | 反復全体の目的をループ直前または本文先頭に記す。 |
| 例外処理 | 対象となる構文の直前または対象ブロックの先頭に、何を回復・変換・記録・解放するかなど、その処理の役割を記す。 |
| 長い直線処理 | 処理段落の先頭に目的を記し、無説明区間が利用先の上限を超えないよう処理のまとまりで区切る。 |
| 順序・データ源・境界などに意味がある処理 | 変更すると何が崩れるか分かるよう、確認できた制約と理由を対象処理の近くに記す。定型の配置検査に含まれなくてもreviewで必要性を確かめる。 |

ファイルヘッダー、ライセンス、宣言のドキュメントコメント、lint抑制指示、空・記号だけのコメント、`TODO`や機械向けタグだけの記述は本文説明の代用にしない。ネストした関数・ラムダ・別ブロックの説明を外側の説明に数えない。文字列中のコメント風の文字も数えない。

## 説明の根拠と改修時の扱い

- コードで確認できる動作と、仕様・契約・採用判断から確認できる理由を区別する。理由が確認できなければ創作せず、判断に必要な不足を明示する。維持に必要なときだけ第三者が辿れる根拠を添える。
- 関係する既存コメントの意味と根拠を変更前に確認する。意図・維持条件・testの期待値を変えるなら、今回の要求と旧判断を変えられる根拠をreviewで確認し、整理だけの差分と混同しない。
- 誤記訂正や正当な仕様変更では説明も同じ論理変更で更新し、無効な説明は削除できる。有効な説明を差分作りのために書き換えず、既存コード全体の一括追記へ広げない。
- コメント率、文字数、固定のwhy欄、出典タグの有無で意味の品質を判定しない。説明が示す保証が実装・test本文にあるかをreviewする。

## テストのドキュメントコメント

守る契約と条件、期待する直接の観測結果、検出したい具体的な故障を自然な文章で読めるようにする。一文で伝わるものを別々の欄へ分ける必要はない。業務上の期待値や回帰の根拠が判断に必要なら、確認済みの仕様・Issue等の該当箇所を示す。重複に見えるtestが必要なら追加の保証を説明し、不要なら説明を書くために残さない。

要求として約束していない現在の挙動を一時固定する場合は見直し条件を、一時検証を残す場合は除去条件を記す。全testに分類・期限・恒久指定は求めない。新規・変更対象から、必要な説明を言語に合うdocコメントとして整える。[テスト変更と保持の判断](test-changes.md)も参照する。

```python
def test_retry_preserves_single_charge():
    """同じ冪等キーで再送しても、公開APIの請求一覧が1件のままであることを確認する。

    再送を新規請求として登録し、二重請求を起こす回帰を検出する。
    期待値は支払い契約の「再送時の冪等性」に基づく。
    """
    ...
```

仕様名と本文は説明例。実変更では確認済みの参照先を示し、再送経路を通ってassertionが二重登録を検出するかを本文から別にreviewする。

## 利用先での機械検査の導入

共通規約を置くだけでは検査は有効にならない。次を利用先の既存設定・規約で確定する。共通の固定値や専用設定形式は設けない。

1. 対象ソース、宣言、制御構文、変更範囲。非公開宣言とtestファイルの適用範囲、呼び出し型testの識別を確かめる。
2. コメントを認める位置・形式、対象の宣言・構文・処理との対応付け。
3. 同一スコープの無説明区間の数え方（行・文・式など）、具体的な上限、長い単一式の扱い。
4. 説明として数えないものと、ネストや別スコープのコメントを外側から除く方法。
5. 除外する範囲と理由。ツールが再生成するファイルと、AIが編集・保守する通常のソースを区別する。個々の変更の都合で設定を緩めたり抑制したりしない。
6. 通常のbuild／lint／検証コマンド、違反で失敗を返す条件、統合経路で必ず確認する検証点。

| 言語 | ドキュメントコメントの候補 | 本文コメントの候補 |
| --- | --- | --- |
| C# | compiler／既存Analyzerの対象宣言を確認 | Roslyn Analyzer等で構文とコメントの対応を判定 |
| TypeScript／JavaScript | 既存JSDoc検査に必要な宣言・test呼び出しを含める | ESLintの既存・カスタムルールで構文とコメントを対応付ける |
| Python | 既存docstring検査の宣言範囲を確認 | 既存lintを使い、不足する配置判定は `ast`／`tokenize` 等で補う |

既存の機構を優先し、不足分だけ補う。文字列検索を構文判定の代用にしない。検査本体は手動・hook・CIで共用し、配置や形式の違反は注意だけでなくコマンドを失敗させる。対象・上限が未設定、対象なし、未実行、対象言語未対応は合格に数えない。規約の整備、端末への配置、利用先での導入と実行の結果を区別する。共通エンジンや一律の注意喚起hookを導入条件にしない。

### 代表例と判定

利用先で検査を導入したら、対応する正常例が通り、代表的な違反例が失敗することを実行して確かめる。意味の確認には既存のreviewを使う。

| 例 | 期待する判定 |
| --- | --- |
| 対象の非公開メソッドにdocコメントがない | 宣言の必須検査で失敗。 |
| 対象testの宣言・呼び出しにdocコメントがない | 宣言の必須検査で失敗。testがlint対象外なら導入未完了。 |
| 対象ループの直前に目的の説明がある | そのループの配置検査を通過。 |
| 対象の分岐の一枝または例外処理に説明がない | 配置検査で失敗。 |
| 関数ヘッダーだけあり、本文の無説明区間が上限を超える | 本文の検査で失敗。 |
| 空コメントや抑制指示だけが置かれている | 本文の検査で失敗。 |
| 内側のラムダにだけ説明がある | 外側の必須条件は満たさない。 |
| 文字列に `// 説明` がある | コメントとして数えない。 |
| 形式は正しいが、未実装の保証や未確認の理由を書いている | 機械検査の通過に関係なくreviewで訂正する。 |
| 正当な仕様変更に伴い旧理由を更新・削除する | 根拠と内容をreviewする。コメント変更そのものは禁止しない。 |
| testの条件・期待結果・検出したい故障が自然なdocコメントで読める | 必要事項を説明できていれば、専用のタグや欄は不要。 |
| 説明は正しいがmockが故障を隠す | reviewでtestの検出力の問題として扱う。 |
| 一時固定を恒久の要求のように説明している | 根拠・見直し条件をreviewし、説明かtestを直す。 |
| 削除する旧testにdocコメントがない | 旧本文と確認できる契約をreviewする。旧側の説明を補作しない。 |
