# UI変更の必須基準

UI設計・実装開始前と変更後の確認時に、変更の影響に該当する範囲を読む。専門判断はruntimeが通知する実pathの`design-ui-information` Skill、製品固有の基準は対象製品側を参照する。

## ユーザー向けUIの必須基準

- UIの新設・変更では、runtimeが通知する実pathの`design-ui-information`と、対象製品のUI規約を参照する。確認範囲は変更の影響に限定し、UIに影響しない変更は対象外とする。
- 実装前に利用者・内容・中心となる体験と、参照する表現方針・共通部品・基準画面を確認する。読む・探す・鑑賞する等のUIを操作効率だけで設計せず、不要な主要操作を設けない。
- 情報と表現の採否・優先順位は実装側で判断する。取得可能な情報や説明の羅列で完成とせず、主内容と補助UIを区別する。不要な内部情報や同じ役割の重複は出さず、本文・作品・必要な説明や識別子は残す。
- 部品の配置前に、意味のまとまり、順序、面積、密度、区切りを設計する。無計画な縦積みやカード化で済ませず、不要な膨張と往復を防ぐ。短さ・情報量の少なさ・特定スタイルを一律の正解にしない。
- 内容に合う文字・余白・色・画像・強弱を選び、製品内で見た目と振る舞いの規則を揃える。同じ役割には妥当な既存表現を使い、差分には内容・体験・要求上の理由を求める。
- 実質的なUI変更は、実描画と閲覧・操作の流れを確認し、見つかった問題は「統合優先・修正分離」で扱う。修正した箇所と影響範囲は再確認する。安全・回復・accessibility等を落とさない。test/build成功を視覚確認の代わりにせず、未確認を残す場合はUI品質確認済みとしない。検証のために操作権限を拡張しない。
