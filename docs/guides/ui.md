# UI変更の判断と確認

利用者に見える内容・文言・見た目・操作を新設または変更するときは、対象製品の規約とruntimeの `design-ui-information` Skillを使う。実際の依頼、合意した用途、観察できた使い方から利用者が何を終えるかを定め、主内容と必要な操作を選ぶ。既存部品や内部データを使うために用途を後付けしない。新たな用途は提案として扱い、任された範囲の通常の実装手段は実装側が選ぶ。文言だけの修正も影響箇所を確認し、UIに影響しない変更にこの工程を課さない。

表示や説明を足す前に、原因となる操作・制約・部品を外せるか考える。外しても必要な結果、安全、状態と回復手段を守れるか確かめ、残る責務を画面に表す。既存機能の配置を完成の前提にしない。

## 主内容と補助説明の境界

記事の本文、作品とその解説、比較に必要な値、操作名など、利用者が読んだり判断したりする対象そのものを用意する。読み上げ名・状態通知、必要な開示、重大な操作を確定する前の対象と影響、失敗後の状態と回復手段は、その機能の一部である。これらを伝える文言は、文の形を取っても補助説明ではない。既存の製品・業務契約に従い、削ったまま完成扱いしない。

補助UIは**作らないところから始める**。データ項目や将来の機能のための枠を用意して、空欄を説明で埋めない。利用者がどこで何を見分けられないかが具体的なら、まず配置・まとまり・順序・強弱で関係を示し、それでも不足するなら対象や操作を表す明確な単語を選ぶ。色・動き・hoverだけに意味を任せない。各案を順番に試作する必要はない。

それでも不足が残り、補助説明が不可欠な場合だけ、必要な事実を最短の文案にして**実装前にユーザーの明示承認を得る**。仕組みの解説・状態への但し書き・免責を足す行為は、一語のバッジ、アイコン、ツールチップ、一時通知に置き換えても同じである。表示の形や長さではなく、何を伝えるための追加かで判定する。

承認が必要な差分だけ、対象画面・状態・文案と、デザインや単語では何が伝わらないかをまとめる。同じ意味・対象範囲で明示承認済みの内容は再承認不要。既存の補助説明を改稿するときも、意味や対象範囲を変える分だけ承認を得る。承認待ちはその補助説明に依存する差分に限り、他の作業は続ける。

## 作業領域と操作の安定

比較・一覧・編集・図など、同時参照が作業に役立つ画面では、利用可能な幅・高さの増加を主要作業領域に返す。親レイアウトの制約も含め、画面を広げても作業に使える領域が不必要に固定されないようにする。自然な余白、読みやすい行長、短いフォームに適した大きさは保ち、空間を埋める表示や単なる拡大を目的にしない。

操作結果などの文言が現れたり消えたりすることで、既存の操作対象を不意に動かさない。利用者が意図した展開・折り畳み、遷移、レスポンシブな再配置は妨げず、位置の安定のために必要なエラーや回復情報を隠さない。

## ローカルでの起動・撮影

対象画面と必要な状態へ手元で到達し、撮影できる既存の開発経路を使う。依存・設定、起動コマンド、確認データ・到達方法と撮影方法は製品のREADMEか開発手順から辿れるようにする。不足は依頼内で整え、本番データや認証・認可の迂回に頼らない。環境整備が依頼範囲を超えるときだけ、必要な変更を示して確認する。

## 実描画と共有

変更後の画面を実際に見て、影響する範囲の主内容、読み順、状態、代表的な閲覧・操作の流れを確かめる。実装案に合わせたデモが動くだけでなく、代表的な条件と状態で元の用事を最後まで行えるかで判断する。遷移や動作を変えた場合は静止画だけで済ませない。実描画・再確認の代わりにbuildや自動testの成功を使わず、操作権限は共通AGENTS.mdに従う。見つかった問題の扱いは[開発guide](development.md)で判断する。

機密・個人情報が写らない状態で撮影し、共有前に実際の画像を確認する。指定がなければ現在のSessionFolderに置き、進捗または完了の返答に `![画面名・状態](<画像の絶対path>)` で埋め込み、見るべき変更点を短く添える。Windowsの区切りは `/` とし、変更前の画像は比較に必要な場合に示す。起動・撮影・共有できなかったときは、何が妨げとなり、確認または共有できない範囲がどこかを伝える。
