# UI変更の必須基準

UI開発環境の整備、UI設計・実装開始前、変更後の確認・報告時に、変更の影響に該当する範囲を読む。専門判断はruntimeが通知する実pathの`design-ui-information` Skill、製品固有の基準は対象製品側を参照する。

## ユーザー向けUIの必須基準

- UIの新設・変更では、runtimeが通知する実pathの`design-ui-information`と、対象製品のUI規約を参照する。確認範囲は変更の影響に限定し、UIに影響しない変更は対象外とする。
- 実装前に利用者・内容・中心となる体験と、参照する表現方針・共通部品・基準画面を確認する。読む・探す・鑑賞する等のUIを操作効率だけで設計せず、不要な主要操作を設けない。
- 利用者の目的と現在の閲覧・操作の文脈から主内容を定め、情報と表現の採否・優先順位は実装側で判断する。主内容を成立させる本文・作品・必要な説明や識別子を示し、補助UIはそこに残る具体的な不足を補う。取得可能な情報や説明の羅列で完成とせず、不要な内部情報や同じ役割の重複は出さない。
- 部品の配置前に、意味のまとまり、順序、面積、密度、区切りを設計する。無計画な縦積みやカード化で済ませず、不要な膨張と往復を防ぐ。短さ・情報量の少なさ・特定スタイルを一律の正解にしない。
- 内容に合う文字・余白・色・画像・強弱を選び、製品内で見た目と振る舞いの規則を揃える。同じ役割には妥当な既存表現を使い、差分には内容・体験・要求上の理由を求める。
- 実質的なUI変更は、実描画と閲覧・操作の流れを確認し、見つかった問題は「統合優先・修正分離」で扱う。修正した箇所と影響範囲は再確認する。安全・回復・accessibility等を落とさない。test/build成功を視覚確認の代わりにせず、未確認を残す場合はUI品質確認済みとしない。検証のために操作権限を拡張しない。

## ローカルでの起動・撮影

UIを扱う開発環境は、手元で対象UIを起動し、確認する状態を再現してスクリーンショットを取得できる構成を基本とする。必要な依存・設定、起動コマンド、確認用データや対象画面への到達方法、撮影方法は、対象repositoryのREADMEまたは既存の開発手順へ記載する。

UI設計・実装の前に既存の起動・撮影経路を確認し、不足は依頼範囲内で最小限に整える。既存の開発用起動経路・撮影手段を優先し、撮影のために本番データや認証・認可の迂回へ依存させない。環境整備が依頼範囲を実質的に広げる場合は、不足と必要な変更を示して確認する。

## スクリーンショットによる認識合わせ

- UI変更では、変更後の画面・状態が分かるスクリーンショットを取得し、内容を実際に見てからユーザーとの認識合わせに使う。軽微な変更は変更箇所と影響に絞り、比較に必要な場合は変更前も示す。
- 取得済みの共有可能な画像は、ユーザーから求められるのを待たず、進捗・完了の返答へ埋め込む。WithMateではMarkdownの画像記法 `![画面名・状態](<画像の絶対path>)` を使い、実在する画像のpathを指定する。Windowsのpathは `C:/...` のように区切りを `/` に揃える。撮影済みという説明、pathの列挙、通常のリンクだけで提示を済ませない。
- 画像には画面・状態と確認してほしい変更点を短く添える。撮影・共有前に機密情報・個人情報の露出を避け、WithMateからSessionFolderが提供されていれば画像はそこへ保存する。保存先の明示指定を優先する。
- 起動・撮影・共有ができない場合は、理由と未確認の範囲を返答へ明記する。撮影の成功を共有・ユーザー確認済みと同一視せず、test/build等で代替してUI品質確認済みとしない。検証や共有のために操作権限を拡張しない。
