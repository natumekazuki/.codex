# テスト変更と保持の判断

残すのは、現在も必要な振る舞いを守るtestである。旧パネルを消した事実だけなら、今回の差分や実描画で確認して終える。そのための恒久test・fixtureを先に作らない。一方、「権限のない利用者には非公開項目を返さない」は、表示や内部実装を替えても有効な契約である。不在という期待値の形だけで、どちらも同じ扱いにしない。

恒久testの価値は、現役の要求・契約、違反による具体的な影響、既存の型・check・testでは検出できない故障、CI・保守の負担が見合うかで判断する。条件、期待する観測、検出したい故障と必要な根拠は[テストのドキュメントコメント](code-comments.md#テストのドキュメントコメント)に記す。削除・非表示後も不在を保証するなら、その理由も分かるようにする。一時検証は目的を果たし、記載した除去条件を満たしたら終了する。

既存の機構が不要なら、それだけを支えたtest・fixtureも同じ論理変更で整理する。testがあるという理由で実装を戻さず、逆に失敗を消すために現役の保証を弱めない。

## 通常のreviewで確認する

実装と同じ差分の中で、テストが守る契約と、想定した故障が実際の実行経路を通ってassertionの失敗として現れるかを確認する。たとえばmockが故障を隠していないか、期待結果をテスト対象と同じ実装から導出していないかを見る。

削除・置換・移設では変更前のテスト本文と根拠も読み、今も必要な保証がどこに残るかを確かめる。移設先でrunnerがそのテストを実行するかも確認する。変更前に説明がなければ、確認できる本文と契約を使い、過去の理由を補作しない。必要なテストの実行結果と、テストが保証を守れるというreviewの判断を区別する。
