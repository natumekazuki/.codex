# 開発・review・統合の判断

実装・課題管理・review・統合・公開の判断に使う。共通の操作権限はAGENTS.md、設計選択と共有方針の草案・採否は[設計判断・文書化](design-decisions.md)に従う。具体的な管理ツールと運用は対象repositoryの正本で確認する。

## 実装の複雑さと責務

- 本来の責務・合意した要求に必要でない追加の保証・制約・防御機構を提案する場合は、具体的な支障・根拠と実装・保守・利用への負担を示し、明示承認を得る。必要性や発生確率を捏造せず、「理論上より安全」だけで範囲を広げない。責務から必要な入力検証・認証・認可・データ保護は通常の実装として満たす。
- 既存の防御処理も、責務と契約から必要性を評価する。不要な状態・分岐・利用側を一体で減らす基準は設計guideに従う。
- 未知の入力は信頼境界で検証し、保証された型・構造を内部へ渡す。保証が有効な内部経路では重複検証を避ける。型注釈・アサーションを実検証の代替にせず、新しい境界・状態変化に必要な検証を残す。
- 補助関数は再利用・合成、複雑な境界の隔離、意味ある命名による見通しを理由に分ける。一度だけの単純処理を先回りで分割せず、主要な流れを埋める処理は切り出す。
- `try/catch`は回復・変換・記録など、その箇所の責務に使う。扱う責務のない例外は既存の境界へ伝播させる。

## 文書と管理データの正本

| 配置 | 責務 |
| --- | --- |
| 共通・プロジェクトのAGENTS.md | 常時原則と条件付き参照の入口 |
| 共通guide | 設計・開発・統合等の判断基準 |
| プロジェクトのREADME・運用文書 | 管理先、予定・公開単位、維持境界、完了条件、変更・承認の具体的運用 |
| 選択された課題管理先 | 個々の課題の予定・状態・関連記録 |
| `SessionFolder/review-results/*.md` | review結果と指摘別対応。後追い課題の管理先を代替しない |

参照先の解決はAGENTS.mdに従う。既存の正本を更新・参照し、入口への手順の重複、別台帳への二重入力、専用ファイル・固定章立ての新設を要求しない。repository内Markdownの課題管理も未完了課題の現行情報を扱う。

## プロジェクトごとに定義する管理観点

実装前に、今回影響する維持対象と残件の管理先を確認する。対象repositoryの既存運用から、作業に関係する管理先、対応予定、branch・タグ・公開単位、維持対象・期間、完了・変更条件、判断・操作権限を辿れるようにする。全項目の毎タスク監査や一括読込は求めない。

不足・矛盾は既存の運用・契約・実際の適用状況を調べて具体案を作り、実際にその判断へ依存する変更・完了判断だけ保留する。管理先に依存せず残件もない変更は進められるが、後追いが必要なら管理先を確定し、実登録して引継ぎを完了する。必須作業の未完了を非ブロッカーへ付け替えない。

取得失敗を未定義・不存在とみなさない。予定未指定を許す定義があればその状態を扱い、管理方法自体の未定義とは分ける。

## 対応予定と完了・公開の判断

予定・優先度・期限・統合可否・公開可否・維持対象を分ける。予定は正本・明示決定・採用済み規則から確認し、調査対象のbranch・version・タグから修正版を推定しない。既定方針や委譲の範囲では判断する。Milestone等の予定単位は任意であり、採用時は作成単位、割当て・変更・未指定、公開単位との関係、クローズ条件を定義する。正式タグの作成前でも予定は管理できる。

公開範囲を決める際は、対象予定の未完了課題と関連する予定未指定の課題を確認する。全バックログの監査や未指定ゼロは条件にしない。

完了は対象コードへの反映と必要な検証で判断し、予定指定・課題クローズ・公開とは区別する。自動クローズもこの基準に合わせる。追加・延期・対象外化・再開は既定の基準と権限に従い、理由と変更後の扱いを正本へ残す。未完了を隠すクローズ・予定移動をしない。

管理方針の採用・統合可能という判断と、外部記録・push・merge・公開の操作承認は別である。権限がなければ提案として扱う。

## 統合優先・修正分離

主要動作、維持境界、後続の合意済み契約、必須確認、統合先を確認し、依頼内の実装・確認が済んだ変更を早期に統合する。review指摘は必要性、対応時期、統合への影響を分けて判断する。

| 扱い | 判断基準 |
| --- | --- |
| 今回の仕上げ | 今回の要求・契約・品質を満たすために必要で、依頼内で完結する不備を直す |
| 後追い | 具体的支障があるが、今分離する理由があり延期できるものを引き継ぐ |
| 不採用・重複 | 根拠のない任意改善は終了し、重複は既存記録へ集約する |
| 未確認 | 判断に必要な不足を調べる。調査を延期する場合も後追いの基準で扱う |

修正の容易さ・発見段階・既存ラベルだけで任意改善を必須化せず、非ブロッカーを一律に後追い登録しない。後追い非該当から即時修正必須とも逆算しない。

統合ブロッカーは、統合後のbuild・起動・必要な組込み、主要動作、後続の合意済み契約の不成立、または根拠のある重大なデータ破壊・情報漏えい・権限逸脱とする。成立しない動作・依存・安全境界と根拠を示し、優先度・差分起因・変更範囲・修正の容易さだけで停止しない。必須確認や依頼の未完了を後追いへ付け替えない。

必要な初回reviewで取りまとめ担当が採否・時期を判断し、修正と影響範囲を確認する。別の採否審査を設けず、追加確認は修正・新変更・競合・check失敗・具体的な安全懸念に必要な範囲へ絞る。局所修正や再開・base更新だけで全体探索をやり直さず、収束しなければ未解決と必要な判断をユーザーへ示す。

後追いは既定の管理先と操作権限の範囲で実登録し、現象・再現状況、影響・起点、分離と延期の理由、完了条件、担当または未割当てを引き継ぐ。完成した原因分析や修正案は登録の前提にせず、登録要否の定型質問へ戻さない。結果と参照先を示し、登録を着手・対応版確定とは扱わない。

ブロッカーがなく、必須確認・引継ぎ・操作権限が揃えば統合し、必要な統合後確認を終える。延期可能な非ブロッカーの修正完了を統合・後続開始・公開の条件にせず、間に合う確認済み修正を取り込み、残りは修正リリース等へ引き継ぐ。mergeが自動公開を伴う場合は公開条件も満たす。新たな重大影響は関連する依存先・公開判断へ反映する。

## SessionFolderのreview記録と対応管理

review結果は現在の`SessionFolder/review-results/`へMarkdownで保存する。他Sessionへ参照を渡す段階では[WithMateの共有基準](withmate.md#sessionfolderとcrew-folder)に従って必要資料の配置と参照を揃える。明示保存先と記録禁止の指示を優先する。保存先が取得できなければ推測・新設せず、結果と保存できない理由を返す。

- 取りまとめ担当（委譲時は親）が終了・中断時に、対象repository・commit・差分範囲、担当、結論、指摘、実施確認を保存し、保存先を伝える。未コミット範囲も識別し、指摘ゼロと未確認・中断を区別する。
- 独立reviewは別ファイル、同じreviewへの対応は同じ文書で扱う。安定した指摘IDに対象・影響・根拠・分類理由・対応状況・修正確認の根拠・引継ぎ先を必要な分だけ記録する。固定章立てや無関係な空欄は設けない。
- 元の指摘と対応後の確認対象を分ける。修正済み・未検証を確認済みにせず、不採用・重複には理由を残す。元の所見を修正後の状態へ書き換えて消さない。
- 結果確認・対応開始／再開・完了判断前に、関連文書の最新版と現在の対象を照合する。保存先は提供情報・Graph参照・現在のreview-resultsから特定する。
- 対応担当は分類・修正・検証・引継ぎの区切りで担当指摘を更新する。共有文書は更新前に読み、変更で確認根拠が失われた範囲を再確認する。
- Graphには結論・未解決の要約と結果ファイル・指摘IDへの参照を置く。指摘別進捗を複製しない。正式な後追い登録後は引継ぎ先を進捗の正本とする。
- 保存・分類の完了と、修正・引継ぎ・統合・公開の完了を分ける。review記録はセッション内の作業資料とし、repositoryへ恒久保存しない。

## 互換性を維持する境界の明示

対象repositoryの入口から辿れる規約に、維持する対象・期間と、それを確定する条件を定義する。維持対象がまだなければその旨と今後の確定条件を示す。曖昧な「必要に応じて判断する」で代用しない。

- 実データ、適用済みmigration、業務上の意味・確定結果・不変条件、認証・認可、利用中の外部契約等を事実と合意から具体化する。
- Gitタグは版を識別するが、配備・利用の証明や実装全体の維持契約ではない。タグのない配備済み環境やRC・STGの保持データも実際の適用状況から扱う。
- 維持契約のない画面配置・文言・導線・内部構造等は改善できる。UIが担う業務承認・実行前確認・公開範囲への影響は評価する。
- 定義した維持対象を除き、開発途中の仕様・実装は直接更新する。途中状態の保護だけを目的とするバージョン更新・移行処理・旧仕様併存を加えない。
- 既存定義で決まる判断は引き受ける。明示された維持契約の廃止・縮小、定義の矛盾、定義外の適用事実が変更可否を左右する時は確認する。仮想的な利用可能性だけで維持境界を広げない。

仕様上の非互換と、実データ破棄・環境再作成の操作権限は別に扱う。
