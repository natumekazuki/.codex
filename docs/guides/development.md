# 開発・review・統合の判断

実装・課題管理・review・統合・公開の判断に使う。共通の操作権限はAGENTS.md、設計選択と共有方針の草案・採否は[設計判断・文書化](design-decisions.md)に従う。具体的な管理ツールと運用は対象repositoryの正本で確認する。

## 実装の複雑さと責務

- 本来の責務・合意した要求に必要でない追加の保証・制約・防御機構を提案する場合は、具体的な支障・根拠と実装・保守・利用への負担を示し、明示承認を得る。必要性や発生確率を捏造せず、「理論上より安全」だけで範囲を広げない。責務から必要な入力検証・認証・認可・データ保護は通常の実装として満たす。
- 既存の防御処理も、責務と契約から必要性を評価する。不要な状態・分岐・利用側を一体で減らす基準は設計guideに従う。
- 未知の入力は信頼境界で検証し、保証された型・構造を内部へ渡す。保証が有効な内部経路では重複検証を避ける。型注釈・アサーションを実検証の代替にせず、新しい境界・状態変化に必要な検証を残す。
- 補助関数は再利用・合成、複雑な境界の隔離、意味ある命名による見通しを理由に分ける。一度だけの単純処理を先回りで分割せず、主要な流れを埋める処理は切り出す。
- `try/catch`は回復・変換・記録など、その箇所の責務に使う。扱う責務のない例外は既存の境界へ伝播させる。

## 文書と管理データの正本

| 配置 | 責務 |
| --- | --- |
| 共通・プロジェクトのAGENTS.md | 常時原則と条件付き参照の入口 |
| 共通guide | 設計・開発・統合等の判断基準 |
| プロジェクトのREADME・運用文書 | 管理先、予定・公開単位、維持境界、完了条件、変更・承認の具体的運用 |
| 選択された課題管理先 | 個々の課題の予定・状態・関連記録 |
| `SessionFolder/review-results/*.md` | review結果と指摘別対応。後追い課題の管理先を代替しない |

参照先の解決はAGENTS.mdに従う。既存の正本を更新・参照し、入口への手順の重複、別台帳への二重入力、専用ファイル・固定章立ての新設を要求しない。repository内Markdownの課題管理も未完了課題の現行情報を扱う。

## プロジェクトごとに定義する管理観点

作業に関係する次の観点を既存の運用で判断できるようにする。全項目の毎タスク監査や全詳細の一括読込は不要であり、範囲が変われば新たに関係する定義を読む。

| 観点 | 定義する内容 |
| --- | --- |
| 管理先 | バグ・要求・後追い残件の正本、分離と重複集約の境界 |
| 対応予定 | 着手・対応順序、割当て・変更・未指定の扱い。予定単位を使う場合はその意味 |
| コードと公開単位 | branch・プレビュー・正式タグ・公開物と予定の関係、反映状態の確認方法 |
| 維持境界 | 互換性・継続性を維持する対象・条件・期間 |
| 完了と変更 | 実装・review・統合・課題完了・公開の条件、延期・対象外化・再開・引継ぎ |
| 権限 | 既定方針・委譲に基づく判断範囲と、記録変更・merge・公開等の操作範囲 |

### 未定義・未指定・未確認と停止範囲

実装前に影響する維持対象と残件の管理先を確認する。不足・矛盾は運用・契約・タグ・実際の適用状況を調べて具体案を作り、その判断に依存する変更・完了判断だけを保留する。独立性は実際の差分と依存先から判断する。

管理先の選択に依存せず、引き継ぐ残件もない変更は進められる。残件登録が必要な場合は管理先を確定し、実際に登録して引継ぎ・統合を完了する。必須作業の未完了を非ブロッカーへ付け替えない。

予定未指定をバックログとして認める定義があれば、その状態を許容する。管理方法自体の未定義や依頼対象・統合先の不明とは分ける。必要な情報を取得できない場合も、未定義・不存在・残件ゼロとは推定せず、依存する判断を保留する。

## 対応予定と完了・公開の判断

予定・優先度・期限・統合可否・公開可否・維持対象を分ける。予定は正本・明示された決定・採用済み割当て規則から確認し、調査branch、package version、直近タグ、発生版から修正版を推定しない。既定方針や委譲の範囲では判断を引き受ける。

Milestone等の予定単位は任意とする。採用時は作成単位、割当て・変更・未指定、branch・タグとの関係、クローズ条件を定義する。正式タグの作成前でも予定は管理できる。

- リリース範囲の確定・公開判断では、対象予定の未完了課題と、予定未指定の関連課題の取りこぼしを確認する。全バックログの監査や未指定ゼロを条件にしない。
- 完了は対象コードへの反映と必要な検証から判断する。予定指定、ローカル編集、課題クローズ、予定単位クローズ、正式公開を区別し、既存のPR・commit・branch等で確認する。重複・不採用クローズを修正完了にしない。
- 自動クローズを使う場合は、その操作条件を課題の完了基準と整合させる。
- 追加・延期・対象外化・再オープンはプロジェクトの基準と権限に従い、理由と変更後の扱いを正本へ残す。未完了を隠すクローズ・予定移動は行わない。

管理方針の採用や統合可能という判断と、外部記録・push・merge・公開の操作承認は別である。権限がなければ提案として扱う。

## 統合優先・修正分離

着手時に主要動作、維持境界、後続の依存契約、必須確認、統合先を確認する。依頼された機能・修正と必要な確認を完了し、動作する変更を早期に統合する。review指摘の採否・対応時期・統合可否は分けて判断する。

| 扱い | 判断基準 |
| --- | --- |
| 今回の仕上げ | 今回の要求・契約・品質を満たす不備で、依頼内の修正と確認で完結するもの。新たな判断が不要なら対応する |
| 後追い | 必要性と放置による具体的支障があるが、規模・依存・調整・差戻し等により今は分ける理由があり、延期できるもの |
| 不採用・重複 | 要求・契約・具体的支障に根拠のない任意改善は終了できる。重複は既存記録へ集約する |
| 未確認 | 判断材料が不足するもの。必要な判断を妨げる不足は調べ、延期する調査は後追い基準で扱う |

非ブロッカーを一律に後追い登録せず、後追いに該当しないことから即時修正必須とも逆算しない。修正の容易さ・発見段階・既存ラベルだけで任意改善を必須化しない。

統合ブロッカーは、対象環境での統合後のビルド・起動・必要な組込み、対象機能または統合先の主要動作、後続に必要な合意済み契約の不成立とする。具体的根拠のある重大なデータ破壊・情報漏えい・権限逸脱も停止対象とする。成立しない動作・依存・安全境界と根拠を示し、優先度・差分起因・変更範囲内・修正の容易さだけで停止しない。

必要な初回reviewでは、取りまとめ担当が指摘の採否・時期・統合への影響を判断する。別の採否審査や分類ごとの承認工程を増やさない。追加確認は修正・新変更・競合解消・check失敗・具体的な安全上の懸念に必要な範囲とし、局所修正や再開・base更新だけで全体探索をやり直さない。収束しなければ未解決事項と必要な判断をユーザーへ示す。

後追いは既定の管理先と操作権限の範囲で登録し、現象・再現状況、影響・起点、分離理由と延期可能な理由、完了条件、担当または未割当てを引き継ぐ。完成した原因分析や修正案を登録の前提にしない。登録するかを定型質問に戻さず、登録結果と参照先を示す。その登録を修正着手・対応版の確定と同一視しない。

後追いの着手・完了を現在の統合や後続開始の条件にしない。ブロッカーがなく、必須確認・引継ぎ・操作権限が揃えば統合へ進み、必要な統合後確認を終えて依存先を着手可能にする。同じ予定単位の非ブロッカーだけで公開を延期せず、間に合う確認済み修正を取り込み、残りは修正リリース等へ引き継ぐ。

必須check・描画確認・操作権限は後追い方針でも満たす。mergeが自動公開を伴えば公開条件も満たす。新たな重大影響が判明した時は、関係する依存先・公開判断を更新する。

## SessionFolderのreview記録と対応管理

review結果は現在の`SessionFolder/review-results/`へMarkdownで保存する。明示保存先と記録禁止の指示を優先する。保存先が取得できなければ推測・新設せず、結果と保存できない理由を返す。

- 取りまとめ担当（委譲時は親）が終了・中断時に、対象repository・commit・差分範囲、担当、結論、指摘、実施確認を保存し、保存先を伝える。未コミット範囲も識別し、指摘ゼロと未確認・中断を区別する。
- 独立reviewは別ファイル、同じreviewへの対応は同じ文書で扱う。安定した指摘IDに対象・影響・根拠・分類理由・対応状況・修正確認の根拠・引継ぎ先を必要な分だけ記録する。固定章立てや無関係な空欄は設けない。
- 元の指摘と対応後の確認対象を分ける。修正済み・未検証を確認済みにせず、不採用・重複には理由を残す。元の所見を修正後の状態へ書き換えて消さない。
- 結果確認・対応開始／再開・完了判断前に、関連文書の最新版と現在の対象を照合する。保存先は提供情報・Graph参照・現在のreview-resultsから特定する。
- 対応担当は分類・修正・検証・引継ぎの区切りで担当指摘を更新する。共有文書は更新前に読み、変更で確認根拠が失われた範囲を再確認する。
- Graphには結論・未解決の要約と結果ファイル・指摘IDへの参照を置く。指摘別進捗を複製しない。正式な後追い登録後は引継ぎ先を進捗の正本とする。
- 保存・分類の完了と、修正・引継ぎ・統合・公開の完了を分ける。review記録はセッション内の作業資料とし、repositoryへ恒久保存しない。

## 互換性を維持する境界の明示

対象repositoryの入口から辿れる規約に、維持する対象・期間と、それを確定する条件を定義する。維持対象がまだなければその旨と今後の確定条件を示す。曖昧な「必要に応じて判断する」で代用しない。

- 実データ、適用済みmigration、業務上の意味・確定結果・不変条件、認証・認可、利用中の外部契約等を事実と合意から具体化する。
- Gitタグは版を識別するが、配備・利用の証明や実装全体の維持契約ではない。タグのない配備済み環境やRC・STGの保持データも実際の適用状況から扱う。
- 維持契約のない画面配置・文言・導線・内部構造等は改善できる。UIが担う業務承認・実行前確認・公開範囲への影響は評価する。
- 定義した維持対象を除き、開発途中の仕様・実装は直接更新する。途中状態の保護だけを目的とするバージョン更新・移行処理・旧仕様併存を加えない。
- 既存定義で決まる判断は引き受ける。明示された維持契約の廃止・縮小、定義の矛盾、定義外の適用事実が変更可否を左右する時は確認する。仮想的な利用可能性だけで維持境界を広げない。

仕様上の非互換と、実データ破棄・環境再作成の操作権限は別に扱う。
