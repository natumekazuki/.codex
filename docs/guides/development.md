# 開発・review・統合の判断

## 実装前に、何を維持するかを確かめる

対象repositoryのAGENTS.mdからREADMEまたは運用文書を辿り、今回影響する維持対象と残件の管理先を確認する。管理先、予定・公開の単位、維持期間、完了・変更条件、判断権限はプロジェクトの正本に置き、課題別の予定と進捗は選んだ管理先にだけ置く。専用ツールや固定章は要らない。Markdownで課題を管理する場合も、残すのは未完了課題の現行情報である。

実データ・適用済みmigration、業務上の確定結果・不変条件、認証・認可、利用中の外部契約など、維持する対象・期間と、それを確定する条件を定める。まだ対象がないなら、その事実と今後の確定条件を示す。Gitタグは版の識別子であって配備の証拠ではない。タグのない環境やRC・STGに実データがあれば、適用の事実を考慮する。

維持契約の外にある途中仕様は直接更新する。途中版のためだけの互換層・併存・移行は作らない。画面配置を変えられても、そこで行う業務承認・実行前確認・公開範囲は別に確かめる。明示された契約の縮小・廃止、定義の矛盾、定義外の実利用が判断を左右するときは、事実に基づく案を示して確認する。非互換を許す判断はデータ破棄や環境再作成の許可ではない。

管理方法の未定義と、一件の予定未指定、正本の取得失敗を区別する。不足を調べたうえで、その判断に依存する部分だけを保留する。管理先を使わず、引き継ぐ残件もない変更まで止めない。

## 実装先と信頼境界

[設計guide](design-decisions.md)に従い、追加・維持する責務が必要かを確かめてから、フロント・バックそれぞれの既存箇所と利用側をたどる。例えば編集経路を一つ増やすなら、フロントは既存の入力部品を使い、バックは保存を担う既存サービスで同じ業務判定を行う。判定を画面ごとに複製しない。既存実装が契約に合わないときは、その担当箇所の更新を検討する。

- 信頼境界で未知の入力を実検証し、認証・認可・データ保護を満たす。型注釈やアサーションは検証ではない。保証が有効な内部経路で同じ検証を重ねず、別の入口や状態変化で保証が失われる所では検証する。
- 長期保守するコードは同じ理由で変わる処理を集め、再利用・合成、意味のある命名、複雑な境界の隔離で流れが明確になる単位に分ける。一度限りの処理や、所有境界の異なる似た処理のために共通層を作らない。
- 例外は回復・変換・記録を担う所で扱い、それ以外は既存の境界へ伝える。失敗を成功に見せる代替値は返さない。
- 本来の責務に必要な安全性・accessibilityは実装に含む。契約にない保証・制約・防御を加えるなら、ないと何が困るか、その根拠と実装・保守・利用者の負担を示して明示承認を得る。

## 実装規約の基本セット

コードの追加・変更・reviewでは、[コードコメント規約](code-comments.md)を読み、変更に関係する範囲へ適用する。

アプリの新規開発・初回整備では次の基本セットを揃え、通常の変更では関係する範囲に適用する。既存設定・ツール・検査を使い、規約と実行方法を対象repositoryの入口から辿れるようにする。

- 書式・命名・lintと、該当する型検査を定める。
- 責務ごとのファイル配置と依存の向きを定める。検査のための層は増やさない。
- ドキュメントコメントで公開API・境界と非公開の主要処理、testの役割・契約を説明する。本文の通常コメントで処理の段落、判断、維持条件を説明する。必須位置の存在・配置・形式は利用先の通常の検証コマンドで検査し、内容の正しさと十分さはreviewで確認する。
- 重要な正常時・失敗時の動作をテストし、自動検査と実機・実環境でしか確認できない事柄を分ける。

機械で判定できる違反は機械検査にする。commit前はstaged差分の高速な検査、push前は対象commitの型・依存の該当検査と単体テスト、merge前は実際の統合候補に必要な検査を行う。同じ検査本体を手動・hook・CIから使い、hookの有効化方法を示す。CIの要否は統合経路に必要な保証で決める。

新設した検査は正常例が通り代表的な違反例が落ちることを確かめる。対象なし・未整備・未実行は通過ではない。通常の実装を既存コード全体の修正や外部設定変更に広げない。

## 統合優先・修正分離

テストの追加・意味変更・削除・移設は、言語を問わず、実装と同じreviewで[守る契約と検出力](test-changes.md#通常のreviewで確認する)を確認する。テスト実行は別に必要な範囲で行う。重大な保証を弱める変更など、通常のreviewだけでは判断できない場合は、影響に応じて独立した担当が確認する。別途必須の独立確認は省かない。

reviewの取りまとめ担当は、今回の要求と維持境界を基準に指摘の採否・時期・統合への影響を判断する。

- **今回直す**のは、依頼の要求・品質・合意した契約に足りない点である。必須の作業や確認が残れば未完了のまま扱う。
- **後追いにする**のは、具体的な支障はあるが、今分ける理由があり延期できるもの。操作権限の範囲で正規の管理先へ実登録し、現象・再現状況・影響・起点、分離理由、完了条件、担当または未割当てを引き継ぐ。原因の確定を待つ必要はない。登録先を示せて初めて引継ぎ済みとなり、着手や修正版の確定は意味しない。
- **採用しない**任意改善には理由を残し、重複は既存の指摘・課題に結び付ける。判断に足りない事実は調べ、調査を先送りする場合も後追いの基準を使う。修正の容易さやラベルだけで全件修正・全件登録にしない。

統合を止めるのは、統合後のbuild・起動・必要な組込み・主要動作・後続の合意済み契約が成立しないとき、または重大なデータ破壊・情報漏えい・権限逸脱に具体的な根拠があるときである。どの動作・安全境界を損なうかを示す。優先度や差分が原因かどうかだけで統合可否を決めない。

必要な初回reviewで判断し、修正・新変更・競合・検査失敗・具体的な安全懸念が影響する範囲を再確認する。別の採否審査や、局所修正・base更新・再開のたびの全面reviewは設けない。収束しなければ未解決点と必要な判断を伝える。

統合先・必須確認・実登録を要する引継ぎ・操作権限が揃い、ブロッカーがなければ早期に統合し、必要な統合後確認を行う。分離できた修正は後続作業や公開の開始条件にしない。間に合う確認済み修正は取り込み、残りは必要に応じて修正リリースへ渡す。mergeで自動公開される場合は先に公開条件も満たす。

## SessionFolderのreview記録と対応管理

取りまとめ担当（委譲時は親）は、reviewの終了・中断時に、現在の `SessionFolder/review-results/` へMarkdownで結果を保存し、保存先を伝える。明示保存先・記録禁止を優先し、保存先が不明なら推測せず、結果と保存できない理由を返す。他Sessionへ渡す資料は[共有基準](withmate.md#sessionfolderとcrew-folder)に従う。

対象repository・commit・差分範囲（未コミット分も含む）、担当、結論と実施した確認を特定する。指摘ゼロは未確認や中断と区別する。指摘があれば安定したIDで元の対象・影響・根拠を残す。分類の理由、修正状況、修正後の対象と確認結果、必要な引継ぎ先を同じ文書に追記し、元の所見は書き換えない。独立したreviewは別ファイルにする。

対応担当は結果確認・対応開始／再開・完了判断の前に、提供された保存先・Graph参照・現在のreview-resultsから最新版を特定し、現在の対象と照合する。分類・修正・検証・引継ぎの区切りで担当分を更新し、共有文書は更新前に読む。修正済みでも確認前なら検証済みにしない。Graphは結論・未解決の要約と結果ファイル・指摘IDへの参照にとどめ、正式な後追い登録後の進捗は登録先で扱う。review記録はrepositoryへ恒久保存しない。

## 完了・予定・公開は別に決める

完了は対象への実装と必要な検証で決める。予定指定、優先度・期限、課題のclose、review完了、統合、公開は別の事実である。自動closeも完了条件に合わせる。調査時のbranch・version・タグから修正版や対応予定を推定せず、正本・明示決定・採用済み規則に従う。

Milestone等を使う場合だけ、作成単位、割当て・変更・未指定の扱い、公開単位との関係、close条件を定める。タグ作成前でも予定は管理できる。追加・延期・対象外化・再開は所定の権限で行い、理由と扱いを正本に残す。未完了を隠すためにcloseや予定移動をしない。

公開範囲を決めるときは、対象予定の未完了課題と関連する予定未指定課題を確認し、新たな重大影響は依存先・公開判断に反映する。全バックログの監査や未指定ゼロを条件にしない。方針の採用・統合可能という判断は、外部記録・push・merge・公開の実行承認にはならない。
