# 開発・review・統合の判断

共通AGENTS.mdの条件付き参照先。課題・対応予定の確認・登録・変更・完了判断前、開発の完了条件を決める時、review開始前、実装変更着手前、リリース範囲の確定・統合・公開判断前、互換性対象の契約を変更する前に読む。実装を伴わない課題管理にも適用する。共通化するのは決めておく事項と判断原則であり、管理ツールや具体的な運用ではない。

共有判断の不足・矛盾、共有方針の新設・変更や、それに伴う現行説明の更新・統合を扱う時は、[設計判断・文書化](design-decisions.md)に従う。実装者とレビュアーは同じ要求・前提と採用済みの判断を使い、過剰設計の指摘も必要な保証と追加負担に照らす。文書の存在だけで必要性や適用済みを証明した扱いにはしない。

## 文書と管理データの正本

| 配置 | 責務 |
| --- | --- |
| 共通の`~/.codex/AGENTS.md` | 常時必要な最小原則、読む条件、共通の詳細文書への入口 |
| 共通の本書 | 各プロジェクトで定義する管理観点とCodexの共通判断原則 |
| 各プロジェクトのAGENTS.md | 常時必要な最小原則、固有の詳細文書を読む条件と入口。共通の入口で明確な定義は再利用する |
| 各プロジェクトのREADMEの節・既存の運用文書等 | 管理先、対応予定の意味、コード・公開単位との関係、完了・公開条件、変更・承認の具体的な運用 |
| 選択されたIssue・Milestone・課題管理ツール・repository内Markdown等 | 個々の課題の現在の予定・状態・関連する記録 |

共通文書は共通AGENTS.mdの指定どおりユーザーhome直下の`~/.codex/`から読む。プロジェクト固有文書は、同入口が示す対象repositoryのREADMEの関連節、または対象repositoryのAGENTS.mdが明示する運用文書を読む。Markdownリンクだけで本文を読み込んだ扱いにせず、配布元`.codex`のREADMEや別プロジェクトの運用で代用しない。

固有の詳細は既存の適切な文書を正本とし、AGENTS.mdへ割り当て・延期・クローズ等の手順を二重定義しない。専用ファイル名、固定の章立て、新規ファイルを要求せず、既存情報への参照で足りるなら書き直さない。「どこで管理するか」というルールと「この課題をどの版へ入れるか」という現在の管理データを分ける。選択された管理先を正本とし、AGENTS.md、README、版別ラベル、独自台帳等への二重入力を要求しない。repository内Markdownを管理先にする場合も、履歴文書を増やさず、未完了の課題の現行情報を扱う。

## プロジェクトごとに定義する管理観点

以下をプロジェクトの運用として判断可能にする。同一の管理工程やツールを導入するテンプレートではない。作業に関係する既存定義・参照を利用し、全詳細の一括読込や全項目の毎タスク監査は行わない。作業範囲が変わった時に新たに関係する詳細を読む。

| 観点 | 定義する内容 |
| --- | --- |
| 課題の管理先 | バグ、機能要求、後追い残件の管理先。分ける場合の境界と重複の集約先 |
| 対応予定の管理 | リリース・バージョン・フェーズ等の予定単位を管理するか。管理する場合の正本、割り当て基準、未指定の意味 |
| コード・公開単位との関係 | 作業ブランチ、統合先、プレビュー、正式タグ・公開物と対応予定の関係。対象コードと公開済み状態の確認方法 |
| 互換性の維持境界 | 開発途中と互換性・継続性を維持する状態を分ける条件・対象。対応予定とは別に定義し、詳細は「互換性を維持する境界の明示」に従う |
| 完了と公開 | 実装・review・統合・課題完了・正式公開の条件。課題や予定単位をいつ、何を根拠に閉じるか |
| 予定変更と残件 | 追加・延期・対象外化・再オープン等の基準、必要な引継ぎ、予定への反映方法 |
| 判断と操作の権限 | 既定方針・委譲に基づきCodexが判断できる範囲と、記録の作成・更新・クローズ・merge・公開等を実行できる範囲 |

対応バージョン等の予定単位を管理しない場合は、その方針を明記すればよい。GitHub Milestone、バージョン付きブランチ、タグ運用、専用の状態ラベルを新設させない。「採用しない」という定義と管理方法の未定義を区別する。

### 未定義・未指定・未確認と停止範囲

- 実装変更前に、変更が影響する維持対象とバグ・後追い残件の管理先を確認する。互換性境界の不足・矛盾が変更可否を左右する場合は、その判断に依存する変更を止める。実際の差分と依存先から独立性を説明できる変更、調査・説明・review・定義の草案作成は進められる。影響が未調査であることを独立性や安全性の根拠にしない。
- 管理先が未定義なら既存の運用・記録を調べ、具体的な配置案を示す。判断を委譲されていれば依頼内で定義できる。引き継ぐ残件がなく、管理先の選択に依存しない変更は進められるが、残件の登録が必要な場合は管理先を確定し、実際に登録するまで引継ぎ・統合を完了扱いしない。未作成・未実行・失敗・成功を区別し、必須作業の未完了を非ブロッカーへ付け替えない。
- その他の管理観点の不足も一律の実装停止条件にしない。例えば対応予定の管理方法が未定義なら、割り当て・延期・公開判断等、その不足に依存する判断・操作だけを保留する。不足に依存しない作業は分けて進める。
- 管理方法が定義済みで、予定未指定をバックログとして認める運用なら、個別課題の未指定だけで規約違反や実装禁止にしない。具体的な作業依頼の対象・統合先まで不明な場合とは区別する。
- 不足・矛盾は取得可能な運用・記録、タグ・契約・適用状況を調べ、推奨案と具体的な草案まで作って未合意の方針だけを確認する。不足の列挙だけを返したり、草案を有効な規約へ昇格させたりしない。
- 必要な文書・外部情報を取得できない場合は未確認とする。未定義・存在しない・残件ゼロとは推定せず、その情報に依存する判断を保留する。

## 対応予定と完了・公開の判断

### 予定と実績を分ける

- 対応予定、優先度、期限、統合可否、公開可否、互換性の維持対象を同一視しない。予定は指定された正本・明示された決定・採用済みの割り当て規則から確認する。
- 調査中のブランチ、現在のpackage version、直近のタグ、発見した環境だけから予定を確定・変更しない。調査対象や発生版の記録を、そのまま修正版の決定に読み替えない。
- 既定方針や明示された判断の委譲で決められる場合は、その範囲で進める。すべての割り当てを新規承認へ戻さない。操作権限は後述のとおり別に確認する。
- 予定の指定は、その版への実装反映・検証・公開の証明ではない。正式タグの未作成だけを理由に予定管理を待たせない。

### Milestone等を採用する場合

GitHub Milestoneは予定を管理する選択肢の一つであり、必須ではない。採用する場合は次をプロジェクト側で具体化する。GitHub以外の管理方式でも相当する観点を使う。

- 作成単位。正式版単位にするか、プレビュー等を別に扱うか。
- 課題の割り当て・変更・未指定の扱い。
- 対象ブランチ・タグ・公開物との関係と、完了・クローズの条件。
- リリース範囲の確定時・公開判断時に確認する残件。

例えば、正式版`v1.2.3`のMilestoneに、その開発ブランチと各プレビューで対応する課題をまとめ、正式公開後にMilestoneを閉じる構成がある。これは説明用の例であり、全プロジェクトの既定値でも、WithMateや配布元`.codex`の採用済み方針でもない。バージョン単位の予定管理を採用しない運用も成立する。

### 取りこぼし防止と完了の根拠

- リリース範囲の確定時・公開判断時は、対象の予定に含まれる未完了課題と、予定未指定のまま今回の対象から漏れている関連課題の両方を確認する。全バックログの毎タスク監査や、未指定を必ずゼロにすることは要求しない。
- 課題の完了はプロジェクトの基準と、対象コードへの反映・必要な検証の根拠で判断する。ローカルで編集しただけの状態を対象リリースへ反映済みとしない。
- 実装済み、課題を閉じた状態、予定単位を閉じた状態、正式公開済みを区別する。重複・不採用等によるクローズを修正完了と同一視しない。
- 未完了件数や進捗率だけで必要な変更が公開対象に含まれると判断せず、既存のPR・commit・対象ブランチ等で必要な反映状況を確認する。新しい状態管理基盤や独自の証跡台帳は作らない。
- 自動クローズを採用するプロジェクトでは、その操作条件と課題の完了基準の整合を確認する。自動クローズ自体を要求しない。

### 予定変更と操作権限

- 追加・延期・対象外化・再オープンは、プロジェクトの基準、既定方針・委譲された判断・必要な承認の範囲で扱う。理由と変更後の扱いを既存の管理先へ残し、残件の引継ぎは「統合優先・修正分離」に従う。
- 残件をゼロに見せるために未完了課題を閉じたり、予定単位を閉じるためだけに別の版へ移したりしない。正当な延期と未完了の隠蔽を分ける。
- 管理先の定義、方針の採用、統合可能という判断は、Issue・Milestoneの作成・更新・移動・クローズ、push、merge、公開等の許可を代替しない。共通AGENTS.mdの操作・対象・scopeへの承認条件を維持する。
- 既に承認・委譲された範囲を文言の違いだけで再確認しない。read-only依頼・権限不足では提案までにとどめ、書込み失敗も含め未実施を明記する。管理先への反映・登録・引継ぎ済みとは扱わない。

## 統合優先・修正分離

- 動作する変更を早期に統合し、後続タスクの依存を解消する。実装、review、後追い修正、統合、公開の完了を分け、review指摘の全件修正を現在の作業の完了・merge・通常のリリースの条件にしない。
- 着手時に既存の要求から主要動作、後続が実際に依存する契約、必須確認、統合先を確認する。依頼機能の未実装や指定されたバグ修正自体の未完了を、後追いへ付け替えて完了扱いしない。
- 統合ブロッカーは、対象環境での統合後のビルド・起動・必要な組込みの不成立、対象機能または統合先の主要動作の不成立、後続に必要な合意済み契約の不成立とする。具体的な根拠のある重大なデータ破壊・情報漏えい・権限逸脱も停止対象とする。停止には成立しない動作・依存・安全境界と根拠を示し、優先度、今回の差分起因、変更範囲内であること、修正の容易さだけでは止めない。
- 必要な初回reviewは対象を確認し、各指摘をブロッカー、後追い、重複、不採用、未確認へ整理して終える。review完了は全件修正やmerge可能を意味しない。非ブロッカーの修正と全体再reviewを元タスクで繰り返さず、通常の後追い分類ごとにユーザー承認を求めない。
- 追加確認はブロッカー修正、新たな変更、競合解消、必須check失敗、具体的な安全上の懸念に必要な範囲へ限定する。再開・base更新だけで確認済み範囲を再探索しない。同じブロッカーへの対応が収束しない場合はユーザーへ未解決事項と必要な判断を報告し、無限反復や未解決の合格扱いに進まない。
- 残件は定義された管理先へ記録し、現象・再現状況、影響、起点、統合を止めない理由、修正完了条件、担当または未割当てを必要な範囲で引き継ぐ。重複は既存の記録へ集約する。根本原因や完成した修正案を引継ぎの前提にせず、未確認・未登録・引継ぎ不能を成功扱いしない。
- 非ブロッカーは現在の作業とは別の修正タスクとして扱い、その着手・完了を現在の変更の完了・統合や後続タスクの開始条件にしない。同じMilestone等の予定単位に未完了課題があることだけで一律に止めない。統合ブロッカーがなく、必要な確認と引継ぎが完了していれば権限の範囲内で統合へ進み、必要な統合後確認が成立したら依存先を着手可能にする。
- 修正タスクでは指定された不具合を解消し、途中で見つけた別の非ブロッカーは分離する。対象外のバグ探索のために作業を延長しない。
- プロジェクトの公開条件を満たす範囲で、同一バージョンに間に合う確認済み修正は取り込み、未完了の非ブロッカーだけで公開を延期せず、修正リリース等へ引き継ぐ。予定の変更は前述の判断・権限に従い、新しい根拠で重大な影響が判明した場合は、関係する依存先と公開の判断を更新する。
- 必須check・描画確認・操作権限を後追い方針で免除しない。失敗・未実施を成功にせず、必須条件や権限による待ちは不具合の分類と分ける。mergeが自動公開を伴う場合は公開条件も満たす。

## 互換性を維持する境界の明示

- 共通または対象repositoryのAGENTS.mdの入口から辿れるREADMEの関連節・運用文書には、開発途中の状態と、互換性・継続性を維持すべき状態を分ける境界を定義する。境界を確定する条件と、その対象を既存の情報から判定できる形で記載する。「必要に応じて判断する」など、判断基準のない記述は定義として扱わない。不足が変更判断に影響する場合の停止と草案作成は前述の「未定義・未指定・未確認と停止範囲」に従う。
- Gitリリースタグは版の識別手段であり、実際の配備・利用の有無を証明せず、そのcommitの実装・UI全体を互換維持対象にしない。一方、タグの有無だけで実際に配備・利用済みのデータや契約を維持対象から外さない。RC・STGの保持データや適用済みmigrationも同様に扱う。
- 維持対象は、実データ、適用済みmigration、業務上の意味・確定結果・不変条件、認証・認可、利用中の外部契約等から対象repositoryの事実と合意に基づいて具体化する。画面配置、文言、導線、入力手順、内部構造は、それ自体に維持契約がなく、保護対象を損なわなければ改善できる。ただし、UIが担う業務承認、実行前確認、情報公開範囲等への影響は評価し、UI変更というだけで契約変更の確認を免除しない。
- 維持対象がまだ存在しないリポジトリでは、その旨と、今後何をもって維持対象を確定するかを明記する。維持対象が存在しないことは、定義の欠落ではない。
- リポジトリで定義した維持対象を除き、開発途中の仕様・実装に対する破壊的変更を許容し、途中状態との互換性は保証しない。依頼範囲内で現在の定義を直接更新し、途中状態を保護するためのバージョン更新、移行処理、旧仕様の併存は行わない。
- 境界の定義と既存情報で判断できる場合は、ユーザーへ再確認せず進める。仮想的な利用可能性を理由に境界を追加・拡大しない。定義の矛盾や、定義に含まれない実際の適用事実が見つかり、変更の可否を判断できない場合に限り確認する。
- ここでいう破壊的変更は仕様・実装上の互換性を失わせる変更を指す。実データの破棄、適用済み環境の再作成、依頼範囲外の変更や操作権限の拡大を許可するものではない。
