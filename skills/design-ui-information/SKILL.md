# Design UI Information

内容と体験に合わせて、何を見せるか、どうまとめるか、どの順序・大きさ・表現で見せるかを選ぶ。利用者に不要情報の選別や関係の突き合わせを押し付けず、見た目と振る舞いを製品全体で揃える。情報の網羅、部品の配置、test/buildやaccessibility検査の成功だけで、UIを設計・確認したことにしない。

対象は業務システムに限らず、Webサイト、記事、作品、商品紹介、検索・閲覧サービス、モバイルアプリ、メディア・娯楽、制作ツールを含む。読む、知る、探す、眺める、比較する、作る、鑑賞する、楽しむことも目的として扱う。操作中心でない画面へ主要ボタンや最短操作経路を無理に設けない。

情報量の最小化、スクロールの排除、装飾の禁止、同一スタイルの強制は目的にしない。本文・作品・意味のある余白や装飾を「操作に直接必要でない」だけで削らず、逆に「体験のため」だけで無関係な要素を追加しない。

適用の有無と確認の重さを分ける。誤字修正や機械的な置換では変更箇所と影響だけを確認し、局所変更を全画面・全状態の監査へ広げない。UIへ影響しない内部処理の変更には適用しない。以下の手順は、依頼範囲と変更の影響に該当する部分へ適用する。

以下の設計・実装基準と必須確認は維持し、確認で見つかった問題の修正時期と統合可否は共通`AGENTS.md`の「条件付き参照」から解決した`docs/guides/development.md`の「統合優先・修正分離」に従う。全ての視覚上の問題を直すまで統合できない、という完了条件にはしない。

## Design authority

表現を選ぶときは、次の順で根拠を評価する。明示要求があっても、安全、accessibility、データ保護、操作権限などの既存制約は維持する。

1. 明示された利用者要求、提供された内容、product・編集・ブランド上の要件
2. 内容の意味、中心となる体験、理解、安全、回復、accessibilityの原則
3. 承認済みの表現方針、design system、token、共通primitiveとcomponent
4. 妥当性を確認できた既存画面、閲覧・操作の慣習
5. 単に頻出している既存実装

既存実装は採用候補であって権威ではない。頻出していることだけを根拠に複製せず、承認済み規約と妥当な既存表現を区別する。不適切なpatternを新しい画面へ伝播させない。変更範囲外の問題は切り分け、無断の全面修正へ広げない。

詳細判断の正本はこのSkill、適用条件は共通`AGENTS.md`、必須基準はその配置元の`docs/guides/ui.md`、製品固有の規約・語彙・共通部品・基準画面は対象製品側に置く。新しいdesign system、専用review Skill、全要素の台帳、自動採点、固定の文字数・カード数・ページ高による制限、常設のCI・画像比較基盤を本Skillだけを理由に導入しない。

## 手順

### 1. 体験と参照基準を確認する

利用者、利用場面、内容の性質、中心となる体験、主内容と補助UIの関係を確認する。操作がある場合は、その結果、前後の画面とのつながり、不可逆または高コストな影響も整理する。

関係する規約、共通部品、token、基準画面、指定されたデザイン資料を読み、今回何を参照するか特定する。基準がない場合は、今回必要な範囲で表現方針を仮置きする。たとえば「作品を主役にする」なら、画像の占有面積、説明の強さ、作品間の間隔まで決める。「落ち着いた」「モダン」といった形容詞だけで終わらせない。

仕様や既存実装から分かることは調べ、不明点が構成・見た目を左右する場合に確認する。毎回長い設計書や不要な質問を増やさず、仮の方針を承認済みとして扱わない。

### 2. 情報と表現を選ぶ

本文、画像・作品、見出し、説明、label、icon、状態、操作、装飾を含めて、次を判断する。

> この内容や表現は、誰に、どの場面で、どのような価値を提供するか。
> 常時見せるのか、必要なときに見せるのか、そもそも表示しないのか。

識別・理解・判断・操作・回復だけでなく、主内容の閲覧、発見、鑑賞、雰囲気や製品らしさも、その内容・要求・表現方針と具体的に結び付いていれば採用理由になる。「取得できる」「項目がある」「念のため」「画面が寂しい」は理由にしない。

役割の見落としを防ぐため、必要に応じて次の分類を使う。分類できること自体を表示理由にせず、操作中心の分類へすべてを押し込めない。

| 役割 | 対象 |
| --- | --- |
| `content` | 本文、物語、学習内容、写真、作品、音声・動画など、読む・見る・鑑賞する対象そのもの |
| `experience` | 内容・編集・ブランドの方針に結び付く雰囲気、演出、装飾、表現上の役割 |
| `task` / `state` / `action` | 今できること、現在の状態や起きたこと、操作名、移動先、操作を示す手掛かり |
| `safety` / `error` | 対象と影響、確認、保持された状態、失敗の理由、回復可能な次の操作 |
| `accessibility` / `legal` | accessible name、説明、非視覚的な代替、同意、必須の開示 |
| `supplemental` | 現在の閲覧・理解・判断には必須でなく、必要時に参照する補足 |

本文・作品解説・学習内容を、長い、または操作に直結しないという理由で`supplemental`へ落とさない。理由、履歴、例、定義も、その画面の主内容や現在必要な材料であれば残す。

採否では、次の境界を確認する。

| 対象 | 判断 |
| --- | --- |
| 内部ID・内部状態・診断情報 | 利用者が必要とする根拠なく通常表示へ露出させない。識別・検索・照合・問い合わせに使う番号まで形式で削除せず、既存契約と用途を確認する。必要なら利用者向けの名称・番号や、区別された診断情報として扱う。 |
| 説明・理由 | labelや状態名の言い換え、見れば分かる操作説明、具体性のない確認要求を反復しない。必要な文脈・理由・影響・次の操作は伝える。不明な原因、架空の実績・評価などを画面を埋めるために創作しない。 |
| 空領域・0件 | 空であることの確認価値に応じて表示・集約・省略する。空分類ごとに大きなsectionを作らない。未取得・読込中・取得失敗・権限不足を正常な0件にせず、絞り込み結果0件と全体0件も分ける。 |
| 重複 | 同じ事実を同じ役割で繰り返さない。比較、スクロール中の文脈維持、独立した操作、安全確認など、その位置で必要な再表示は残す。 |
| 取得上限・同期・補助機能の制約 | 仕組みではなく利用者への影響を示す。実表示件数・総件数・取得上限を混同しない。補助機能だけの制約はその操作の近く等で必要な範囲に示し、主内容を押し下げない。主内容の利用や信頼性を損なう制約は隠さず、未提供機能を提供済みに見せない。 |

後付けのUI説明と主内容を区別する。分かりにくさを説明文や注意書きで埋める前に、階層、label、対象と操作の関連、配置を直す。短いlabelで意味が明確になるなら使い、文字を減らすために曖昧なiconやtooltip依存へ置き換えない。

Progressive disclosureは、現在は不要だが別の時点で価値がある情報に使う。不要情報をすべて折りたたみへ移すことは取捨選択ではない。詳細の入口は発見可能かつ支援技術から到達可能にし、本文、作品、比較材料、今必要な理由、安全・回復・必須の開示を隠さない。この基準を満たすためだけに、採否の説明を画面へ加えたり、全要素の恒久台帳を作ったりしない。

### 3. 意味のまとまりと画面全体のcompositionを設計する

部品を置く前に、内容の関係と全体の構成を決める。ここでのブロックは意味や体験のまとまりであり、カード、枠線、HTMLのblock要素、実装componentと同義ではない。APIやDBの分類をそのままsectionへ変換しない。

まとまりの内部では、見出しと本文、画像と説明、対象と操作などを関連付ける。まとまり同士では、順序、面積、主従、区切り、連続性を設計する。単位は一つの判断・操作に限らず、章、作品群、話題、読み進める順序、鑑賞の流れから選ぶ。部品単体が整っていても、ページ全体が成立したとは扱わない。

- **順序と主従:** 最初に何が目に入り、何を主内容と受け取り、その先をどう読む・見渡す・移動するかを決める。全要素を同じ強さにしたり、補助UIで主内容を下方へ追いやったりしない。
- **大きさと密度:** 見出し・本文・画像・補助UIへ役割に合う面積を配分する。小さな補足を大きな領域にし、主内容を狭い領域へ押し込む構成を見直す。
- **連続と区切り:** 一緒に読む・見るものを過剰に分断せず、話題の変化は示す。同じ箱の縦積みや、変化のためだけの配置変更ではなく、内容に合う反復と強弱を選ぶ。

枠やカードを付ける前に、近接、整列、余白、文字の強弱で関係を示せるか検討する。ただし、装飾やsurfaceを常に禁止する段階表にはしない。縦積み、横並び、グリッド、表、カード、タブ、詳細表示、別ページは、同時参照の必要性、読む順序、鑑賞・探索の方法、表示幅に応じて選ぶ。

#### 縦方向の長さ

内容を読む・見るための長さと、未整理な構成による不要な長さを区別する。ページ高ではなく、不要な通過・往復・開閉・分断が体験を妨げていないかを見る。

長くなった場合は、sectionの細分化、見出し・説明の反復、入れ子の余白、過大な固定高さ、行高、折り返し、横幅の配分、補助領域の位置を確認する。短い内容を一つずつ大きな見出し付きカードや画面高の領域へ展開しない。

記事や作品を読み進める長さ、一覧を探索する長さ、まとまり・可読性・強調・雰囲気のための余白は残す。単一カラムや反復グリッド自体を悪い構成としない。横幅の利用も検討するが、本文の行を無理に長くしたり、順番に読む内容を並列化したりしない。

文字の縮小、余白の一律削減、全領域の折りたたみ、固定高さの内部スクロールへ押し込むだけでは改善と扱わない。同時に見たいものを分離して、スクロールを記憶・画面切替の負担に置き換えない。狭幅でも単に全要素を縦積みにして終わらず、読む順序・主従・まとまりを保つ。「スクロールなし」を一律の完成条件にしない。

### 4. 視覚表現を仕上げる

情報を削ったことや共通部品を使ったことと、視覚的に仕上がったことを分ける。文字の大きさ・太さ・行間・行長、余白の比率、整列、色とコントラスト、画像の選択・比率・切り抜き、強弱、必要な動きを、手順1の表現方針へ対応させる。

文字、icon、画像、色、motionに固定の優先順位を付けない。本文や短いlabelを使うことは妥協ではない。Icon-only controlは意味が伝わり、他のiconと区別できる場合に使い、accessible nameを残す。色だけを唯一の手掛かりにしない。

カード、枠、背景、shadow、radius、余白、装飾は、内容のまとまり・鑑賞・編集・ブランド・操作に役割があれば使う。フラットな単一surface、端まで広がるlayout、カード不使用、大きな余白を全UIへ強制しない。逆に、大きな導入領域、定数のカード列、装飾背景をすべての画面へ機械的に当てはめない。入れ子や装飾の重ね掛けで主従を弱めない。

Framed layoutを選ぶ場合は外側の背景も設計する。Popover、menu、dialog等は周囲との層・操作の関係を表す。端・四隅・safe areaの意図しない背景露出や切れ、画像の不適切な切り抜きは実描画で直す。読みやすさや操作性を犠牲にして見た目だけを整えない。

「洗練された」といった自己評価ではなく、表現方針と描画の具体的な一致を見る。作品中心なのに説明や装飾が画像より目立つ、落ち着いて読む方針なのに見出し・色・動きが競合する、といった不一致を修正する。

### 5. 製品全体の見た目と振る舞いを揃える

関係する既存画面と比べ、共通のshell・navigation、情報の階層、文字と余白の体系、色、icon、画像の扱い、用語、操作位置、feedback、画面遷移を揃える。一覧の密度、日付・件数・単位、状態や空表示も、同じ意味・役割では妥当な既存表現に対応させる。

既存token、primitive、component、variantで表せる場合は再利用する。画面ごとに同等部品や独自値を作り直さない。同じtokenを使っていても、主従、見出し、密度、画像のトーン、語彙、操作が無関係に変われば一貫性を満たさない。

一貫性は同一layoutではない。読む、探す、鑑賞する、設定する画面では構成が異なってよい。新しいpatternには、既存では満たせない内容・意味・操作・編集・ブランド・体験上の要求、変更範囲、共通に保つ規則を示す。「このページだけ見栄えをよくしたい」「生成しやすい」は理由にしない。

基準がなければ今回必要な最小の表現方針と再利用範囲を定める。見た目だけが似た別責務の部品を無理に統合せず、共通基盤の新設や全画面展開は依頼範囲として合意されている場合に限る。製品固有の規則を全製品共通の既定値にしない。

### 6. 状態・安全・accessibilityを同時に設計する

変更の影響に応じて、通常、空、読込中、成功、エラー、利用制限、部分データを扱う。補助機能だけが使えない場合と、主内容を利用できない場合を分け、影響と可能な次の操作を必要な位置で示す。

Loadingは処理範囲と進捗の性質に合う表現を選ぶ。部分待機には対象control・領域のspinner、内容取得には最終layoutに合うskeleton、計測できる進捗にはprogress bar、背景処理には主内容を妨げないstatus表示などを検討する。計測していない割合や残時間を創作しない。

待機表示と同じ意味の説明は重ねないが、文字を一律に禁止しない。待つ理由、対象、入力や再試行など、理解・判断に必要なlabelと説明を残す。Screen reader向けのstatus通知、busy state、実際の進捗値を維持する。長時間化、停止、失敗を待機表示で隠さず、既知の状態と回復可能な次の操作を示す。

破壊的・重大な操作では確定前に対象範囲と影響を示し、利用可能な取消・undo・回復方法を明確にする。エラーでは失敗した対象、保持された状態、可能な次の操作を示す。不明な原因は創作しない。

Native control、visible focus、accessible name、論理的な読む順・focus順、contrast、色以外の手掛かり、画像の適切な代替、hover以外の操作経路を維持する。一時surfaceはplatform慣習に沿って閉じられるようにする。文字拡大やlocalizationで内容を失わない。Accessibilityと必須の開示は後回しにせず、情報整理・視覚表現と同時に満たす。

適用要件と変更対象に必要なkeyboard操作・focus管理を保つ一方、全画面のkeyboard監査、新しいshortcut体系、keyboard E2E基盤を毎回追加しない。業務・制作ツール、keyboard中心の利用、custom widget等の要求に応じて検証範囲を選ぶ。

### 7. 実描画と流れを確認し、問題の扱いを決める

実質的なUI変更では、許可されたscreenshotまたはlive renderの内容を実際に見て確認する。通常状態に加え、長文・長い名称、多い内容、空、読込中、失敗、利用制限、狭幅、文字拡大などから、今回壊れやすい条件と代表viewportを選ぶ。全状態・全画面の網羅は要求しない。

最初の表示範囲や部品単体で終わらせず、ページ全体と代表的な閲覧・操作の流れを見る。スクロールのあるUIは途中・下部・区切りも確認する。遷移が変わる場合は前後のつながりを、操作・motionが変わる場合は実際の振る舞いを確認し、静止画だけで済ませない。

| 観点 | 描画で確かめること |
| --- | --- |
| 内容と体験 | 主内容やその画面らしさが不要情報・説明・補助機能に埋もれていないか。読む・鑑賞する等の目的に不要な操作誘導を加えていないか。 |
| 構成と長さ | 関係、順序、面積、密度、区切りが適切か。不要な膨張、往復、開閉、分断、折り返しによる対応関係の崩れがないか。 |
| 視覚表現 | 文字・余白・色・画像・整列・強弱が表現方針に合うか。切れや背景露出、見た目の不調和を「機能はある」で放置していないか。 |
| 一貫性 | 参照した基準画面・規約・共通部品と、見た目・語彙・操作の規則がつながるか。理由のある差分と単なる不統一を分けられるか。 |
| 整理による欠落 | 本文・作品・必要な説明・比較情報・識別子・安全・回復・accessibility・必須の開示・詳細への経路を失っていないか。 |

見つかった問題は共通の統合基準で分類する。必要な内容や主要な閲覧・操作経路、対象利用者の必要なaccessibilityが成立しない問題を、UIという分類だけで非ブロッカーにしない。ブロッカーは修正箇所と影響範囲を再確認し、補助表示の乱れ等の非ブロッカーはプロジェクトで定義した管理先へ記録して引き継ぐ。変更範囲内・容易に直せるという理由だけで、統合前の修正と全体確認を繰り返さない。範囲外の問題は切り分け、無断で作業を広げない。

スクリーンショットの取得だけ、test/build成功、DOM・accessibility・interaction testの成功を、視覚品質の確認済みと読み替えない。利用者調査を実施していないのに、使いやすさや好みが実証されたとは報告しない。

描画確認できない場合は、理由、実装済み範囲、実施した代替確認、残る視覚上の未確認を分けて報告し、UI品質確認は未完了として残す。代替確認は描画確認を免除する条件ではない。検証のために操作権限を拡張せず、Computer Useに必要な明示指示など既存の境界を守る。

参照した基準、確認したviewport・状態・流れ、修正と再確認、後追い先、未確認を、PR説明など既存の記録先へ簡潔に残す。描画確認済みで非ブロッカーが残る状態と、描画未確認を区別する。専用の恒久台帳や採点表は作らない。

## 判断チェック

- 画面の中心となる体験と主内容を捉え、操作効率や特定スタイルだけへ狭めていないか。
- 情報・表現の採否に具体的な理由があり、不要な内部情報・説明・重複を利用者に選別させていないか。
- 部品内部とページ全体を設計し、必要な長さや余白を保ちつつ、不要な膨張・往復・分断を直したか。
- 情報削減や部品再利用だけで止めず、内容に合う文字・画像・余白・色・強弱まで仕上げたか。
- 妥当な製品内規則を使い、同じ役割の見た目・用語・振る舞いを揃え、理由のある構成差を保ったか。
- 本文・作品・比較材料・必要な識別子・安全・回復・accessibility・必須の開示を失っていないか。
- 実描画と必要な流れを確認し、ブロッカーの修正・再確認と非ブロッカーの引継ぎを分け、確認できない範囲は未確認のまま報告したか。
