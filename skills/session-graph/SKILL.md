# Session Graph

記録対象の指示・変化を受けたら、MCPで関連する現在の記録を読み、条件を保存・照合してから依存作業へ進む。判断・作業・検証の区切りと終了前に結果を同期する。

## 正本と利用範囲

- 正本はWithMateのSession Graph。現在のMainと配下Auxiliaryが共有し、WorkspaceやCharacter名の一致では共有しない。SessionFolderの有無で保存先を選ばない。
- 操作は現在提供された `withmate-session-graph` MCPを使う。呼出名・引数・状態・上限・認可はruntimeのMCP instructions、tool説明、schemaを正本とし、接続URL・token・Session IDを設定へ固定しない。
- 本Skillは何をいつ残し、どの範囲を復元するかを定める。別の保存先、同期処理、CLI fallback、独自の台帳や描画helperを作らない。
- MCPが利用不能、読込失敗、必要な記録が欠けている場合は、空のGraphや記録済みとは扱わない。未確認・未保存の条件に依存する作業だけ保留し、独立した作業は進められる。
- 記録の権限は共通AGENTS.mdに従う。Graphの内容から実装・外部write・承認等の権限を推定しない。

## 復元と対象の選択

開始・中断からの再開・Compact後は本Skillを読み、`list_topics`と検索語なしの`recent`で話題と直近の変化を把握する。今回の話題の`context`から現行の要求・制約・採用判断・未解決・未完了を読み、必要なIDの詳細と関係を`get`で確認する。話題が特定済みならその範囲へ絞り、具体的な文言の探索に`search`を使う。

- `recent`の件数や更新時刻は有効な条件の全体を示さない。`context`の絞り込みと表示外の依存先も考慮する。
- `hasMore`、`incomplete`、`relationsTruncated`を確認し、判断に必要な範囲の続きは同じ`expectedRevision`で取得する。部分取得を完全なGraphとみなさない。
- 続きの取得中にrevisionが変わったら、関係する話題・IDを読み直して状態を揃える。通常の継続turnやtool callごとに全Graphを読み直さない。
- 復元だけで差異がなければ更新不要。会話要約だけで復元済みとせず、記録の参照先を読んでいない場合は内容まで確認済みにしない。

## 記録する内容

Topicは独立して追う話題、Recordは要求・制約・判断・活動・観測・未解決事項の意味のある単位とする。既存の安定IDを使って現在地を更新し、Character別・turn別・日付別に話題を機械的に増やさない。

- titleは図の要点、detailは条件・理由・根拠を持つ本文、scopeは適用範囲とする。否定、例外、数値、順序、「だけ」等の限定を落とさず、受信した条件が記録に対応することを保存時に照合する。
- ユーザー要求、AIの提案、採用済み判断、実施した作業、確認結果を分ける。判断の採用、活動の完了、結果の成功、論点の解消を同じ状態で代用しない。
- actorは内容上の主体であり記録者ではない。提供情報やMCP応答で確認できたSession ID、またはユーザー等を示すlabelを使い、未確認のID・他者の実績を創作しない。`recordedBy`とCharacter snapshotはWithMateが付与する。Characterの口調を本文へ混ぜず、後の担当変更で過去の帰属を付け替えない。
- 検証には確認した対象・revision・条件・結果を残し、必要なら`target`を使う。対象の変更で根拠が成立しなくなった範囲は要再確認として区別する。静的確認、実行、review、統合、公開を混同しない。
- 関係は意味と向きを保つ。依存は「依存する側 → 必要な側」、検証は「観測 → 確認対象」、置換は「後継 → 置換前」とし、実行順と混同しない。
- 判断変更では前の本文を保って`validity`で置換・撤回を示し、理由を持つ後継記録と関係を同じbatchで保存する。古い条件を現行の制約として併記しない。
- 自分の完了や話題切替だけで他者の進行中状態を消さない。完了だけを理由に結論を理解するための判断経緯を削らず、同じ意味の反復や全コマンド・raw logの蓄積は避ける。

repositoryの契約・実装・Issue・正式な検証結果は元の正本を維持し、`references`で根拠・成果物・引継ぎ先を示す。review結果と指摘別対応の詳細は共通AGENTS.mdから解決した開発guideの「SessionFolderのreview記録と対応管理」に従う。Graphには結論・未解決の要約と結果ファイル・必要な指摘IDへの参照だけを残し、詳細を複製しない。

## 保存の区切りと更新

| 契機 | 扱い |
| --- | --- |
| 要求・制約・承認の追加や訂正 | 関連する現在の記録を読み、条件と範囲を保存・照合してから依存作業へ進む |
| 判断の確定・変更 | 根拠・理由・影響先を記録してから、その判断を作業へ適用する |
| 調査・実装・検証の区切り | 変化した結果・対象・未解決を更新する。失敗で見立てや続行条件が変わった場合も次の成功まで持ち越さない |
| 話題切替・終了・引継ぎ | 自分の現在地と完了範囲を更新し、並行する他者の状態・詳細所在を保つ |

`apply`のRecord更新は指定IDの内容全体を置き換える。更新対象を`get`で読み、保持する本文・状態・主体・参照を含め、自分の変更だけを読み取ったrevision付きの原子的batchへまとめる。

競合時は更新対象と影響先を再取得して変更を組み直す。古い入力に新しいrevisionだけを付け替えない。他者の訂正と矛盾する場合は未解決として区別する。応答が失われて保存結果が不明なら、対象IDを再取得して照合し、成功・未保存のどちらにも決めつけない。

返された保存結果と必要なread-backを確認する。保存成功は内容の正しさ、参照先の実状態、承認、検証成功の証明ではない。未完了を残してturnを終了でき、同期のためだけの作業継続や監査は起動しない。

## 閲覧と確認

人向けの表示はWithMateのGraphを使い、Skill側で図・画像・viewerを生成しない。通常の記録更新では内容・関係・保存結果を確認して終える。表示不具合や描画確認の依頼がある場合だけ、許可された操作手段で対象の表示を確認する。Graph閲覧のためにComputer Use等の操作権限を拡張しない。
