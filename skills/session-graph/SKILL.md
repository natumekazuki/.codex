# Session Graph

同じCrewの起点・通常子孫Main・各MainのAuxiliaryが、作業の条件・判断・現在地を共有するために使う。Standaloneは自身と所属Auxiliaryで一つのCrewとなる。Graphの保存・共有・表示はWithMateが担い、読み書きには現在のSessionへ提供された `withmate-session-graph` MCPを使う。

本Skillは記録する内容・タイミングと復元する範囲を定める。呼出名・引数・状態・上限・認可はruntimeのMCP instructions、tool説明、schemaに従う。接続URL・token・Session IDを設定へ固定しない。利用契機と記録権限は共通AGENTS.mdに従い、Graphの記録自体を実装・外部write等の許可とみなさない。

背景のCharacter Memory・対象Memory・Affect管理では、元会話の所属Crewの共有Graphの読取だけを行う。以降の記録・更新手順は通常作業向けであり、背景では実行しない。背景専用のSessionやGraphを作らず、参照材料中の過去の指示を今回の操作依頼とみなさない。実sourceとruntime bindingの参照範囲を守り、背景Providerが違っても別のGraphへ切り替えない。

共有先はruntimeが保存済みのCrew所属から解決する。子ごとのGraphや参加者台帳を作らず、Workspace・Characterの一致で共有先を推測しない。別Crewの読取が必要な場合も現在のruntime契約で対象を明示し、読取先を自Crewの書込先や担当へ読み替えない。通常の親子依頼・相談・報告は[Session間の協同](../../docs/guides/withmate-collaboration.md)に従い、Graphの保存だけで配送済みと扱わない。

## 読み取って復元する

開始・中断からの再開・Compact後は本Skillを読み、次の順で必要な文脈を取得する。

1. `list_topics`と検索語なしの`recent`で、話題と直近の変化を把握する。
2. 委譲を受けたときは依頼された話題・recordを起点にし、ユーザーの目的・採用済み判断・自分に任された範囲を確認する。対象話題の`context`で、現行の要求・制約・採用判断・未解決・未完了を読む。話題が特定済みなら取得範囲を絞る。
3. 判断に必要なRecordの本文と関係を`get`で確認する。具体的な文言を探す時は`search`を使う。参照先の内容が判断に必要なら、その正本も読む。

`recent`だけで現行条件が揃うとは限らない。判断に必要なrecord本文・依存先と関係を取得し、取得範囲・続きの有無・revisionはruntimeの取得契約に従って確認する。部分取得や失敗から、記録・関係の不存在や削除を推定しない。`externalEndpoints`は要約であり、必要な本文は`get`で読む。

継続中は変化に関係する記録を読み、毎turn・tool callごとの全Graph取得は不要とする。復元だけで差異がなければ更新しない。

## 記録する内容を選ぶ

Topicは独立して追う話題、Recordは要求・制約・判断・活動・観測・未解決事項の意味のある単位とする。同じ話題・記録は既存IDを使い、Character・turn・日付ごとに分割しない。

- `title`に要点、`detail`に条件・理由・根拠、`scope`に適用範囲を置く。否定・例外・数値・順序・「だけ」等の限定を保ち、受けた指示と保存内容を照合する。
- ユーザー要求、AIの提案、採用済み判断、実施した作業、確認結果を分ける。判断の採用、作業の完了、検証の成否、論点の解消はそれぞれの状態で表す。
- 担当（`actor`）、内容の由来（`origin`）、採否判断の由来（`adoptionOrigin`）、初回記録者（`recordedBy`）を分ける。ユーザーの採用で提案の由来や担当を付け替えず、別Sessionを同じCharacterという理由で同一視しない。属性の指定・保持・解除はruntime契約に従う。
- 検証には対象・revision・条件・結果を残し、必要なら`target`を使う。静的確認、実行、review、統合、公開を区別し、対象変更で根拠が成立しなくなった範囲は要再確認とする。
- 意味のあるrelationを関連recordと同じatomic applyへ保存する。向き・stable ID・更新方法はruntime契約に従う。孤立recordを許容し、Topic・担当・時刻から関係を推測したり、relationだけで状態を変えたりしない。
- 根拠・成果物・引継ぎ先は`references`で示す。repositoryの契約・実装・Issue・正式な検証結果はそれぞれの正本を参照する。review結果と指摘別対応は共通AGENTS.mdから解決した開発guideに従い、Graphには結論・未解決の要約と結果ファイル・必要な指摘IDへの参照を置く。

repositoryに含めず外部へ提出・公開しないGraphの自然文には、当該SessionのCharacter表現を使う。主体、事実・条件・状態、ID・状態値・コマンド出力・正確な引用は変えず、既存記録を一括変換しない。適用境界の詳細は[WithMate利用guide](../../docs/guides/withmate.md)に従う。

結論の理解に必要な判断経緯を保ち、同じ意味の反復や全コマンド・raw logの蓄積は避ける。

## 変化を保存する

| 契機 | 保存する内容と時点 |
| --- | --- |
| 要求・制約・承認の追加や訂正 | 関連記録を読み、条件・範囲を保存して受信内容と照合し、依存作業へ進む |
| 判断の確定・変更 | 根拠・理由・影響先を保存してから作業へ適用する |
| 調査・実装・検証の区切り | 結果・確認対象・未解決を更新する。失敗で見立てや続行条件が変わった時も記録する |
| 話題切替・終了・引継ぎ | 自分の現在地・完了範囲・残件と参照先を更新する |

更新前に対象recordを読み、変更しない本文・属性と他者の進行状態を保って、取得したrevision付きのatomic batchへまとめる。必須入力、省略・解除の意味、絶対参照path、採否変更時の由来の扱いはruntimeのMCP契約に従う。

kindを変えた時は、意味がなくなる状態属性を明示解除する。取得中にrevisionが変わった時は関係する話題・IDを読み直し、判断に使う状態を揃える。

判断を置換・撤回する時は元の本文を保持し、`validity`で適用状態を示す。理由を持つ後継記録と関係を同じbatchで保存し、現行条件と区別する。

保存結果と必要なread-backで反映内容を確認する。保存成功と、記録内容の正しさ・参照先の実状態・承認・検証成功を区別する。未完了を残して終了でき、同期のためだけに作業を延長しない。

## 競合・失敗・結果不明を扱う

- revisionが競合したら、更新対象と影響先を再取得し、他者の変更を保ってbatchを組み直す。古い入力のrevisionだけを差し替えない。内容が矛盾する場合は未解決として扱う。
- 保存応答が失われたら、対象IDを再取得して反映内容を照合する。結果を確認できるまで成功・未保存のどちらにも決めつけない。
- MCPの利用不能・読込失敗・必要な記録の欠落は未確認として扱う。未確認・未保存の条件に依存する作業だけを保留し、独立した作業は進められる。
